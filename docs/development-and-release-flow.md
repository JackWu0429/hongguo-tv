# 已确认功能与统一发布线

`main` 是所有平台共同的正式源码线。工作树和功能分支用于隔离开发，不是功能的长期存放位置，也不决定用户是否收到新版。

## 功能确认后

1. 在当前工作树完成改动和必要验证，并提交到功能分支。
2. 功能确认后，把该提交通过 PR 或等效审查合入 `main`。这一步只整合源码，不打版本标签、不构建正式安装包，也不代表已经发版。
3. 后续工作树从最新 `main` 建立。这样新工作树自然包含此前确认但尚未发布的功能。
4. 切换或删除工作树前，检查 `git status` 与 `git log origin/main..HEAD`。已确认的提交必须已进入 `main`；仍在审查中的提交保留在分支上。

## 正式发布

- 只有用户明确要求发布时，才递增版本号并在 `main` 的提交上创建 `vX.Y.Z` 标签。
- Android、macOS/Windows 和 webOS 的正式构建都以同一个 `vX.Y.Z` 源码提交为准；桌面及 webOS 可以产出自己的平台资产或测试标签，但不能从未合入 `main` 的功能分支发布。
- GitHub Actions 会拒绝从非 `main` 手动发布，也会拒绝不属于 `main` 历史的 `vX.Y.Z` 标签。
- 功能合入 `main` 后到正式标签之间的版本，是“已确认、待发布”状态。它可继续集成后续确认功能，不要求为了保护代码而立即发版。

## 工作树恢复

如果某功能只存在于旧工作树，先查分支提交与 `main` 的差异，不要重写功能。能确认的提交直接合入 `main`；有冲突时以当前 `main` 为基线，将该提交重新应用并保留原提交说明。完成整合后再继续后续功能。
