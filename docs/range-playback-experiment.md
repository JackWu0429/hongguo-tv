# Automatic Range Playback

The WebView/Media3 and MPV players automatically try the same Range playback path; there is no user-facing experiment switch. The core keeps the MP4 initialization section and sample index in memory, then fetches upstream byte ranges as the player requests them. CENC AES-CTR samples are decrypted in the local proxy without saving the complete media file.

Range mode is accepted only when the upstream honors HTTP 206, returns a strong ETag and stable total length, places `moov` before `mdat`, and uses the currently supported whole-sample `senc` layout. Subsample encryption, changed ETags, invalid sample tables, unsupported box layouts, and servers that ignore Range use the existing whole-file download and decrypt path. A speculative Range preparation is Range-only: failure is silent and never starts a full-episode download. Foreground playback falls back to the existing whole-file path if preparation is unsupported or a media error occurs. After playback has produced output, a stalled MPV stream waits 40 seconds and WebView/Media3 waits 45 seconds before fallback; the MPV window covers the Range proxy's bounded retries/resume. Before first output, MPV's separate 25-second output-ready timeout can trigger the same fallback earlier.

Each upstream media range retries transient network/read failures up to two times, with short bounded delays and a 12-second request timeout. If a response is cut off after returning some bytes, the next request starts at the first missing byte instead of downloading that prefix again. A recovered connection can continue that in-flight range without restarting the episode. If retries expire, the active player engine uses the existing whole-file preparation path and restores the last playback time after metadata loads. The MPV edition remains MPV; only its source changes from Range reads to the complete downloaded/decrypted MP4. The standard downloader does not resume a partial on-disk file, and Range media bytes are not persisted, so a long outage or app restart may require a fresh full download on fallback.

Signed URL refresh re-resolves the same VID and quality, then requires the content key, ETag, and total length to match before continuing. Range metadata counts against the existing 512 MiB cache budget and expires after 15 idle minutes. It does not persist media bytes.

For same-series episode changes in Range mode, the current frame is paused and held while the next source is prepared. The loading state starts immediately, but its spinner and target-episode label stay visually hidden for the first 320 ms to avoid a flash on quick switches. If preparation takes longer, the indicator appears; it remains until the new source reports a real presentable frame. The delay only postpones showing the indicator; it never hides loading based on a timer or infers readiness from a URL/progress clock. This is a continuity of state and presentation, not a promise of zero loading time.

Before replacing an HTML5 source, the UI captures its displayed frame into a temporary canvas. This canvas stays above the opaque reset cover until the new video passes the existing presentation gate and paint boundary. It therefore covers the interval where assigning `src`/calling `load()` discards the old video frame and would otherwise expose black or a vendor player placeholder. Manual selection, natural next episode and rapid repeat selections share this path; rapid selections retain the last displayed frame, rather than a partially prepared new source. First load and a different series keep the existing poster behavior.

The captured buffer keeps the video's aspect ratio, is limited to 1280 pixels on its longest edge and 921600 pixels total (about 3.7 MB for RGBA pixels), and is never encoded, saved or uploaded. Explicit contain geometry handles portrait/landscape video, fullscreen and sidebar changes without requiring old WebViews to support `object-fit`. New-frame presentation, playback failure, another series/account, background and page exit clear the buffer. Native Media3/MPV surfaces are not captured; unsupported/tainted canvas reads retain the existing black protection and continue playback. Browser fixtures verify pixels after source replacement and cleanup, but do not prove frame capture works on a particular Android hardware-video compositor.

Automated tests cover byte-range responses, transient recovery, validator checks, sample indexing, partial-sample AES-CTR offsets, header patching, and fallback prerequisites. They do not establish Android TV decoder or WebView behavior; physical-device playback still needs verification.
