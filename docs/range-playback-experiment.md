# Automatic Range Playback

The WebView player automatically tries Range playback; there is no user-facing experiment switch. The MPV edition continues to use its existing player path. The core keeps the MP4 initialization section and sample index in memory, then fetches upstream byte ranges as the player requests them. CENC AES-CTR samples are decrypted in the local proxy without saving the complete media file.

Range mode is accepted only when the upstream honors HTTP 206, returns a strong ETag and stable total length, places `moov` before `mdat`, and uses the currently supported whole-sample `senc` layout. Subsample encryption, changed ETags, invalid sample tables, unsupported box layouts, and servers that ignore Range use the existing whole-file download and decrypt path. A speculative Range preparation is Range-only: failure is silent and never starts a full-episode download. Foreground playback may fall back to the standard path if preparation is unsupported, a media error occurs, or playback remains stalled for 45 seconds.

Each upstream media range retries transient network/read failures up to two times, with short bounded delays and a 12-second request timeout. If a response is cut off after returning some bytes, the next request starts at the first missing byte instead of downloading that prefix again. A recovered connection can continue that in-flight range without restarting the episode. If retries expire, foreground playback uses the standard whole-file path and restores the last playback time after metadata loads. The standard downloader does not resume a partial on-disk file, and Range media bytes are not persisted, so a long outage or app restart may require a fresh full download on fallback.

Signed URL refresh re-resolves the same VID and quality, then requires the content key, ETag, and total length to match before continuing. Range metadata counts against the existing 512 MiB cache budget and expires after 15 idle minutes. It does not persist media bytes.

For same-series episode changes in Range mode, the current frame is paused and held while the next source is prepared. The loading state starts immediately, but its spinner and target-episode label stay visually hidden for the first 320 ms to avoid a flash on quick switches. If preparation takes longer, the indicator appears; it remains until the new source reports a real presentable frame. The old frame is replaced only when the new source is ready to attach. The delay only postpones showing the indicator; it never hides loading based on a timer or infers readiness from a URL/progress clock. This is a continuity of state and presentation, not a promise of zero loading time.

Automated tests cover byte-range responses, transient recovery, validator checks, sample indexing, partial-sample AES-CTR offsets, header patching, and fallback prerequisites. They do not establish Android TV decoder or WebView behavior; physical-device playback still needs verification.
